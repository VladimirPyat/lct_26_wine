Ниже — компактная рабочая схема для первого цикла. Она отделяет базовую адаптацию к phone-domain, очистку retrieval от неродственных визуальных соседей и финальную настройку структуры `same SKU > near >> far`.

Настоящие размеченные phone→catalog пары: **Dev-A = 25** для контроля после эпох и выбора checkpoint; **Dev-B = 27** для подтверждения результата после окончания каждой фазы. Неразмеченный набор заказчика — только после выбора финальных кандидатов.

## Общие правила

### Данные

```
Customer catalog:
  ~2k чистых catalog images, по одному на SKU

External train pairs:
  C — внешний catalog/web image
  P — соответствующее реальное phone фото

Customer train identities:
  C — catalog image
  A1 — pseudo-phone augmentation №1
  A2 — независимая pseudo-phone augmentation №2
```

Для external real-pair identity используем:

```
C — чистая catalog/web картинка
A1 — pseudo-phone аугментация C
P — реальное phone фото
```

У каждого identity всегда **3 views**, а у каждого anchor — **2 positives**.

```
Customer SKU:
  {C, A1, A2}

External pair:
  {C, A1, P}
```

Все embeddings L2-normalize. Search — cosine similarity между phone-query и 2k чистыми catalog embeddings.

### Базовые метрики

После каждой эпохи:

```
1. Закодировать все 2k clean catalog images.
2. Закодировать 25 real phone query из Dev-A.
3. Выполнить полный cosine search 25 × 2k.
4. Сохранить checkpoint, метрики и ranking CSV.
```

Главные метрики:

|Метрика|Смысл|
|---|---|
|R@1 / Top-1|Правильный SKU на первом месте|
|R@5|Правильный SKU есть среди пяти кандидатов|
|MRR|Насколько высоко target в ранжировании|
|Median rank|Типичная позиция correct SKU|
|`score_true`|Cosine query ↔ true catalog SKU|
|`best_wrong_score`|Самый высокий cosine среди неверных SKU|
|`true_gap`|`score_true - best_wrong_score`|
|Top-5 CSV|Разбор конкретных ошибок|

Не задаём фиксированный target cosine вроде 0.65. Контролируем относительный порядок и rank среди полного каталога.

## Фаза 1 — SupCon domain adaptation

**Цель:** стабильно сблизить clean catalog, pseudo-phone и реальное phone представления одного SKU.

### Loss

Обычный multi-positive SupCon:

```
same identity / same SKU:
  positives

all other SKU in batch:
  negatives
```

На этой фазе пока нет кластеров, soft-negative правил и margin hierarchy.

### Состав batch

При batch около 30 изображений:

```
10 identity × 3 views = 30 изображений
```

Пример состава identity:

```
7 customer catalog SKU:
  C + A1 + A2

3 external real-pair SKU:
  C + A1 + P
```

Долю external identity можно варьировать, но стартовать разумно с 20–40% identity в batch: их мало, но они содержат единственный настоящий signal `catalog ↔ phone`.

### Обучение

```
Start:
  pretrained DINO + LoRA

Epochs:
  минимум 2–3, максимум 8–10

Learning rate:
  базовый LR текущего обучения

Mining:
  отсутствует
```

### Контроль

После каждой эпохи — retrieval на Dev-A.

Переходить дальше, когда:

```
- R@5 на Dev-A перестал расти 2 эпохи подряд;
- либо R@1/R@5 начинают ухудшаться;
- либо достигнут max epoch budget.
```

Выбираем лучший checkpoint `M1` по:

```
Primary:   R@5 Dev-A
Secondary: R@1, MRR, median rank
```

После фиксации `M1` делаем **один confirmation run** на Dev-B из 27 реальных phone фото.

## Подготовка графа похожести

Строится после Phase 1 по checkpoint `M1`.

### Что кодируем

```
Все ~2k clean catalog images.
```

### Как строим связи

1. Для каждого SKU найти top-20 nearest different SKU по cosine.
2. Оставить mutual-kNN связи: `A→B` и `B→A`.
3. Добавить manufacturer / бренд, если metadata доступна.
4. Сформировать локальные visual groups:
    
    - same manufacturer + mutual visual edge → `near_brand`;
    - другой manufacturer + mutual visual edge → `near_visual`;
    - остальные SKU → `far`.
5. Сделать contact sheets плотных групп и top-neighbor clusters.
6. Удалить из train известные duplicates, aliases и ошибочные catalog assets.

Не нужно вручную размечать 20k пар. В первую очередь проверяются группы и top-neighbors товаров, присутствующих в Dev-A/Dev-B и в retrieval ошибках.

## Фаза 2 — Hard-FAR negatives

**Цель:** убрать из retrieval неродственные, но визуально случайно близкие товары; сохранить near SKU для будущего shortlist.

### Loss

Пока всё ещё обычный SupCon:

```
same SKU:
  positives

far SKU:
  normal negatives
```

`near_brand` и `near_visual` **не выбираются специально** как hard negatives.

### Hard-FAR pool

Для каждого SKU `A`:

```
top-50 nearest catalog candidates
- true SKU
- near_brand neighbours
- near_visual neighbours
- duplicates / bad data
= nearest remaining candidates
→ сохранить top-10 как hard_far_pool[A]
```

### Состав batch

Пример для 10 identity / 30 views:

```
2–3 anchor identity
+ для каждого anchor 1–2 sampled SKU из его hard_far_pool
+ остальные identity — random far SKU
```

Важное ограничение: sampler должен не просто «случайно надеяться», что hard negative окажется в batch, а гарантировать его присутствие.

У всех identity по-прежнему 3 views:

```
customer:
  C + A1 + A2

external:
  C + A1 + P
```

### Обучение

```
Start:
  лучший checkpoint M1

Epochs:
  обычно 2–4

Learning rate:
  0.3–0.5 от LR Phase 1

Hard-FAR pool update:
  каждые 2 эпохи
```

### Контроль

На Dev-A после каждой эпохи:

```
R@5              — не должен падать
R@1 / MRR        — должны расти или не деградировать
Median rank      — должен снижаться
true_gap         — должен расти
FarLeak@5        — доля far SKU в Top-5, должна снижаться
```

`FarLeak@5` считается только для query, где известны near-группы.

Фаза завершена, если:

```
- R@5 / MRR перестали улучшаться 2 оценки подряд;
- FarLeak@5 перестал снижаться;
- либо R@1/R@5 начали ухудшаться.
```

Лучший checkpoint `M2` выбираем прежде всего по R@5 Dev-A, затем MRR/R@1. Затем один раз проверяем `M2` на Dev-B.

## Фаза 3 — Hierarchical margin shaping

**Цель:** построить конечную геометрию:

```
\text{same SKU}
>
\text{near brand / line}
>
\text{near visual motif}
\gg
\text{far SKU}.
```

Эта фаза не обязана давать максимальный standalone Top-1. Она нужна, чтобы Top-5 был полезным для OCR-реранкера и включал релевантные варианты товара, а не случайные товары.

### Loss

```
L =
L_{\text{masked SupCon}}
+
\lambda L_{\text{relation margin}}.
```

#### Masked SupCon

```
same SKU:
  positives

near_brand / near_visual:
  исключить из SupCon denominator
  не считать positives

far:
  обычные SupCon negatives
```

#### Relation-aware margin loss

Для anchor `q`, true catalog `p`, близкого неправильного SKU `n_\text{near}` и far SKU `n_\text{far}`:

```
L_\text{margin}=
\max(0,m_\text{near}-s(q,p)+s(q,n_\text{near}))
+
\max(0,m_\text{far}-s(q,p)+s(q,n_\text{far})).
```

Начальные значения для абляции:

|Связь|Margin|
|---|---|
|`near_brand`|0.03–0.05|
|`near_visual`|0.05–0.08|
|`far`|0.15–0.20|

Начальный вес:

```
λ = 0.1–0.25
```

### Состав batch

На anchor SKU нужны не только views этого SKU, но и relation candidates:

```
Anchor A:
  C_A + A1_A + A2_A

Near candidates:
  1–2 SKU из near_brand / near_visual graph

Far candidates:
  2–4 SKU:
  - nearest из hard_far_pool[A]
  - плюс random far SKU
```

Каждый candidate identity также приходит со своими тремя views. Loss использует:

```
same identity views:
  positives

near candidates:
  margin only, no standard SupCon repulsion

far candidates:
  SupCon negatives + large-margin comparisons
```

### Обучение

```
Start:
  лучший checkpoint M2

Epochs:
  обычно 2–4

Learning rate:
  0.1–0.3 от Phase 1 LR

Hard-FAR pool:
  можно обновлять каждые 2 эпохи
```

### Контроль

На Dev-A после каждой эпохи:

|Метрика|Ожидаемая динамика|
|---|---|
|R@5|Не падает, желательно растёт|
|R@1 / MRR|Не деградируют существенно|
|Family@5|Растёт|
|FarLeak@5|Падает|
|`true - near` gap|Малый, но положительный|
|`true - far` gap|Больше `true - near`|
|`near - far` gap|Положительный|
|NearSat|Доля соблюдённых near-margin constraints растёт|
|FarSat|Доля соблюдённых far-margin constraints растёт|
|OrderRate|Доля случаев `true > near > far` растёт|

Определения:

```
\text{NearSat}
=
\Pr[s(q,p)-s(q,n_\text{near}) \ge m_\text{near}],
```

```
\text{FarSat}
=
\Pr[s(q,p)-s(q,n_\text{far}) \ge m_\text{far}],
```

```
\text{OrderRate}
=
\Pr[
s(q,p) >
\operatorname{median}s(q,N_\text{near}) >
\operatorname{median}s(q,N_\text{far})
].
```

Лучший checkpoint `M3` выбирается так:

```
Primary:
  R@5 Dev-A

Constraints:
  R@1 не должен заметно ухудшиться
  Family@5 растёт
  FarLeak@5 уменьшается

Tie-breaker:
  MRR и median rank
```

После завершения — единичная confirmation-проверка M3 на Dev-B.

## Финальный выбор

Не обязательно один checkpoint окажется лучшим во всех режимах:

|Checkpoint|Вероятная роль|
|---|---|
|M1|Лучший чистый phone→catalog retrieval после domain adaptation|
|M2|Лучший embedding для самостоятельного Top-1|
|M3|Лучший generator Top-5 для OCR-реранкера|

Финально сравните M1/M2/M3 на Dev-B и выберите один или два режима для последнего ручного evaluation.

## Неразмеченный eval заказчика

Использовать только в самом конце.

Для каждого phone-query сохранять contact sheet:

```
query image
top-1 SKU + cosine
top-2 SKU + cosine
...
top-5 SKU + cosine
top1-top2 gap
```

Ручная проверка:

```
1. Exact catalog hit.
2. Верный SKU находится в Top-5.
3. Top-5 — полезный похожий shortlist.
4. Товара нет в catalog / exact SKU не найден.
```

Для query, где правильный товар есть в catalog, визуально подтвердите retrieval. Для неочевидных случаев — проверьте по названию, сорту, объёму и другим данным каталога. Так вы получите финальную реальную оценку без загрязнения обучающего и validation цикла.
